# Codex Subagent Coordination

Codex coordinates reusable Sol, Terra, and Luna agent archetypes. Each spawned instance is a temporary worker assigned to one bounded repo lane, not a permanent project team.

The Sol Main Agent owns Human communication, semantics, contracts, work decomposition, integration, final architecture consistency, validation, and the final report. Terra is the default repo-aware implementer, while Luna executes narrow contract-bounded work.

<Aside type="caution" title="Single visible owner">

Even if Codex uses multiple subagents, the delivered change must read as one coherent update. The final response must identify what changed, what was verified, and what remains risky or unverified.

</Aside>

## Current Policy

| Concern | Rule |
| --- | --- |
| Sol Main Agent | owns Human communication, semantics, contracts, lane selection, integration, conflict resolution, validation, and final report |
| Terra | default repo-aware implementer for established contracts and non-trivial repository work |
| Luna | narrow executor for explicit, mechanically verifiable work packages |
| Spawned instances | temporary lane workers created from reusable Sol, Terra, or Luna archetypes; use the smallest pool that covers separable work |
| `Plans/` coordination files | retired; do not create new active plan artifacts |
| Direct `develop` work | allowed when the working tree stays coherent and touched-area checks are run |
| Final accountability | Sol and the current conversation own the integrated result |

## Sol Main Agent Responsibilities

Sol must:

- read the relevant SoT before assigning or doing work;
- define the current vertical slice, product semantics, contracts, and success criteria;
- choose whether Terra or Luna work lanes are useful;
- keep subagents inside folder structure and owner-boundary rules;
- reconcile cross-lane conflicts;
- run or account for touched-area validation;
- produce the final integrated report.

Sol does not perform the main feature implementation by default. Sol may write contract documents and scaffolds, and may implement feature logic directly only when the Human explicitly requests it or when implementation cannot yet be separated safely from unsettled semantics.

## Subagent Work Lanes

Map Terra or Luna instances to these repo lanes. The archetype identifies the worker's capability; the lane identifies its temporary repo scope. Use the smallest pool that covers separable work.

| Lane | Typical surfaces | Responsibilities |
| --- | --- | --- |
| Julia Core + Pluto Research | `core/julia/SuperconductingCircuitsCore/`, `notebooks/pluto/` | Julia Core APIs, Pluto direct research workflow, JosephsonCircuits.jl validation, component/circuit prototypes, research sweep and analysis prototypes |
| Product Async Contracts | `docs/app/architecture/contracts/`, `app/backend/app_backend/domain/runtime_contracts/`, `app/backend/`, Backend API contracts | simulation request contracts, runner task envelopes, runner result manifest, result-view API, OpenAPI alignment |
| Backend + Runner Integration | `app/backend/`, `core/julia/SuperconductingCircuitsRunner/`, `data/staging/`, `data/trace_store/` | task lifecycle, runner claim/heartbeat/progress/cancellation/complete/fail, task dispatch, Zarr staging, manifest validation, Backend publication |
| Application Workbench | `app/frontend/`, `app/desktop/` | Simulation Workbench UI, task submission UI, task status/result viewer, Raw Data Browser integration, Electron runtime shell |
| Python Notebook / Data Inspection | `notebooks/python/`, notebook reference docs | programmable data analysis, direct local/exported/canonical data reads, Backend API use for platform state, migration/debug/emergency analysis |
| Docs / SoT Consistency | `README.md`, `docs/`, `site/astro.config.mjs`, `site/src/content.config.ts`, `.agent/rules/**` | SoT consistency, forbidden-regression searches, navigation, guardrail mirrors, stale architecture cleanup |

## Lane Rules

Subagents must:

- stay inside the assigned surface and owner boundary;
- have one primary owner for every modified path, with explicit allowed and forbidden paths;
- not coordinate directly with other subagents;
- avoid redefining architecture or product semantics;
- report `inspected_files`, `changed_files`, `produced_artifacts`, `validation`, and `blockers` back to Sol;
- escalate cross-boundary conflicts instead of patching around them;
- avoid creating persistent prompt bundles or committed lane handoffs.

Do not let two implementers modify the same path unless Sol explicitly sequences their work. Subagents may recommend follow-up work, but Sol decides whether it belongs in the current vertical slice.

## Escalation

- Luna escalates to Terra if its scope expands, a new dependency or public API change appears necessary, or a failure exposes implementation uncertainty.
- Terra escalates to Sol and the Human when product semantics, public contracts, data or state ownership, or architecture boundaries are undefined.
- Sol returns unclear design decisions or acceptance semantics to the Human instead of inventing behavior.

## Vertical Slice Rule

A product feature may span several lanes. For example, a real frequency-sweep workflow touches async contracts, Backend/Runner integration, Application Workbench, and Docs/SoT consistency.

Do not let each lane independently define its own version of the workflow. Sol owns the end-to-end contract and validates the integrated result.

## Handoff

Prefer concise in-thread summaries over committed planning files:

- `inspected_files`;
- `changed_files`;
- `produced_artifacts`;
- `validation` commands and results;
- `blockers`, including known risks or skipped checks.

Long-term decisions belong in `docs/reference/**`, not in temporary planning artifacts.
