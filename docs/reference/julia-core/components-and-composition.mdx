# Components and Composition

Julia Core reusable components are plan-stamping builders. An `add_...!`
function adds relations and engineering records to a caller-owned
`CircuitPlan`, then returns a typed handle that exposes the attachments and
child handles needed by the enclosing topology.

The current implementation does not retain a generic component tree and the
compiler does not recursively flatten one. Composition is ordinary builder
calls that produce one inspectable flat plan.

## Ownership Boundary

The accepted eligibility rule remains:

- a stable local topology reused by a larger circuit topology may enter the
  Julia Core reusable catalog;
- a complete Project Plan Builder, including project ports, targets, study
  policy, or simulation intent, remains outside Core;
- an eligible lab, process, or device-family variant may remain in an external
  Component Library when that is the better owner;
- a compiled netlist fragment is not a reusable component.

Specificity alone does not exclude a reused local topology from Core. See
[Component Libraries](component-libraries.md) for the accepted ownership
decision table.

## Executable Composition Model

```text
caller-owned CircuitPlan
  <- Core relation and transmission-line builders
  <- basic reusable add_...! builders
  <- composite reusable add_...! builders
  <- project-owned complete Plan Builder
```

A reusable builder follows this contract:

1. accept the caller's `CircuitPlan`;
2. enforce its documented ID, attachment, value, and child-handle
   preconditions;
3. create topology through Core relation, transmission-line, or lower-level
   reusable builders;
4. record the public engineering component when the component owns such a
   record;
5. return a typed handle with the public attachments and child handles needed
   by its caller.

Internal node and relation IDs are created by the owning builder and prefixed
with its component ID. Callers connect through returned attachments instead of
depending on those internal names.

<Aside type="caution" title="Builders are not transactional">

Builders mutate the supplied plan as they compose relations. A later
validation error does not guarantee rollback of earlier mutations. Build a
candidate on a fresh plan and discard or rebuild that plan after a failed
builder call.

</Aside>

<Aside type="caution" title="Typed handles are not a retained hierarchy">

A composite result may store child handles for inspection. For example,
`IntrinsicInterferometricPurcellFilterWithQubit` stores the filter and qubit
handles. The electrical relations already live in the same supplied
`CircuitPlan`; there is no later hierarchy-expansion pass.

</Aside>

## Current Catalog Strata

| Stratum | Current examples | May depend on |
| --- | --- | --- |
| Kernel relations and distributed-line builders | capacitive and inductive relations, transmission-line ladders, coupled transmission windows | lower Core authoring primitives |
| Basic reusable builders | `add_parallel_lc_resonator!`, `add_linearized_floating_qubit!`, `add_interdigitated_capacitor!`, `add_reflective_jpa!`, `add_half_wave_resonator!`, `add_quarter_wave_resonator!` | Kernel and distributed-line builders |
| Composite reusable builders | intrinsic interferometric Purcell filter families, filter-with-qubit families, readout-line Purcell and QWR/MTL compositions | Kernel plus basic or lower composite builders |
| Project Plan Builders | complete research circuits and their project-owned ports, targets, and intent | Public Julia Core catalog and selected external libraries |

These strata describe dependency direction, not four required Julia modules.
The current source keeps the reusable builders in
`src/components/reusable_components.jl` and loads transmission-line support
before that file.

## Source-Backed Examples

The interdigitated capacitor builder stamps its three-branch positive
equivalent into the supplied plan and returns the actual terminals and branch
handles:

```julia
idc = add_interdigitated_capacitor!(
    plan;
    id="feedline_idc",
    terminal_1=filter_attachment,
    terminal_2=feedline_attachment,
    c1g_f=C1g,
    c2g_f=C2g,
    c12_f=C12,
)
```

The intrinsic filter builder calls lower-level quarter-wave resonator,
coupled-window, and interdigitated-capacitor builders. It contains no feedline
or port:

```julia
filter = add_intrinsic_interferometric_purcell_filter!(
    plan;
    id="purcell_filter",
    readout_attachment=readout_attachment,
    feedline_attachment=feedline_attachment,
    readout_spec=readout_spec,
    filter_spec=filter_spec,
    mtl_model=mtl_model,
    c1g_f=CpG,
    c2g_f=CfcG,
    c12_f=Cpfc,
)
```

The filter-with-qubit builder accepts an already-built filter handle, verifies
that it belongs to the same `CircuitPlan`, and adds the qubit topology to that
plan:

```julia
system = add_intrinsic_interferometric_purcell_filter_with_qubit!(
    plan;
    id="readout_system",
    filter=filter,
    island_1=q1,
    island_2=q2,
    c01_f=C01,
    c02_f=C02,
    c12_f=C12,
    cr1_f=Cr1,
    cr2_f=Cr2,
    l_j_per_junction_h=Lj,
)
```

The exact topology, defaults, and exclusions for this family are documented in
[Intrinsic Interferometric Purcell Components](intrinsic-interferometric-purcell-components.md).

## Dependency Rules

| Rule | Required behavior |
| --- | --- |
| One direction | Kernel → basic reusable → composite reusable → project plan is a consumer direction; dependencies point back toward the left. |
| No project back-edge | Julia Core must not import a host Project, project Plan Builder, or external lab library. |
| Caller owns the plan | Reusable builders mutate only the supplied `CircuitPlan`; they do not create a hidden second plan or netlist. |
| Attachments stay explicit | Composite builders accept or return actual endpoint and child handles needed for composition. |
| IDs stay local | A builder owns and prefixes private node, relation, and child IDs; callers must not construct against those names. |
| Shared topology moves down only when reused | If two real components need the same local topology, extract one lower reusable builder; do not make the two composites depend on each other. |
| Registration stays outward | Public exports, docs registries, and drawing registries may enumerate completed components; component implementation must not import those registries. |

Before adding a component, draw its dependency edge. Reject the placement if
the edge points from Core to a project/library owner or from a lower stratum to
a higher one. This keeps catalog growth acyclic without introducing a runtime
hierarchy framework.

## Inspection And Compilation

The caller validates and compiles the completed plan once:

```julia
validate_authoring(plan)
inspect_plan(plan)
inspect_endpoints(plan)

compiled = compile_to_josephson(plan)
compiled.netlist
```

Use `EngineeringGraph` and schematic export for Human inspection. Use the
compiled netlist as a separate solver-facing electrical projection of the same
plan, not as a second source of truth. A renderer may arrange or label the
plan, but it must not add connectivity.

## Candidate Semantic Status

- Scope: Julia Core Reusable Catalog Dependency Layering V1.
- Prior evidence: the accepted Core eligibility rule and current plan-stamping
  implementation; the prior page described a nonexistent retained hierarchy
  and compiler flattening pass.
- Existing accepted scope: Core eligibility for stable local topologies reused
  by larger topologies remains `STABILIZED`.
- Current candidate scope: dependency strata and source-backed composition
  description are `CONVERGING`.
- Intended public behavior: builders stamp one caller-owned flat
  `CircuitPlan`, return typed inspection handles, and depend only on lower Core
  strata.
- Failure behavior: builders enforce their documented preconditions, but do
  not promise transactional rollback after a later failure; callers discard
  or rebuild a partially modified plan. Catalog review rejects dependency
  back-edges into projects or higher strata.
- Test policy: `no_test_writes`; existing source inspection and documentation
  checks are diagnostic evidence only.
- Excluded: moving Julia source, adding a generic component tree, changing
  public Julia APIs, and moving project Plan Builders into Core.
- Unresolved: Human acceptance of the dependency-layering candidate.
